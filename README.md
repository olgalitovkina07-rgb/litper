# Справочник контактов

Лабораторные работы №1–6, **вариант 4 «Справочник контактов»**.

Проект разделён на два независимых Gradle-приложения:

- `litper-server` — Spring Boot REST API (модель, Trie, CSV/JSON/бинарь, миграции);
- `litper-client` — JavaFX-клиент, который работает с сервером только по HTTP.

Клиент не зависит от серверных классов: обмен идёт через JSON и DTO.

Корень `litper` — только агрегатор для IDE (`settings.gradle.kts` с `includeBuild`).
Сборки остаются независимыми: у `litper-server` и `litper-client` свои
`settings.gradle.kts`, `build.gradle.kts` и Wrapper.

## Требования

- JDK 21+ (рекомендуется 25) — проверено на JDK 21
- Остальные зависимости подтягивает Gradle Wrapper автоматически

## Запуск

Проект состоит из двух независимых Gradle-проектов, у каждого свой Wrapper.

### Сервер (`litper-server`)

```bash
cd litper-server
gradlew.bat bootRun        # Windows (или gradlew.bat serverRun)
```

Сервер поднимается на `http://localhost:8080`, REST API — на
`http://localhost:8080/api/contacts`.

### Клиент (`litper-client`)

```bash
cd litper-client
gradlew.bat clientRun      # Windows (или gradlew.bat run)
```

Клиент — JavaFX-приложение, подключается к `http://localhost:8080`.
Сервер должен быть уже запущен.

### Сборка и тесты

```bash
cd litper-server
gradlew.bat build
gradlew.bat test

cd ..\litper-client
gradlew.bat build
gradlew.bat test
```

Из корня можно собрать оба проекта сразу:

```bash
gradlew.bat buildAll
```

### Замеры и эксперименты из отчёта (в `litper-server`)

```bash
gradlew.bat benchmark          # своё Trie против TreeMap из java.util (10^4 и 10^5)
gradlew.bat raceDemo           # гонка потоков без синхронизации и защита в Trie
gradlew.bat sampleCsv          # большой тестовый файл data/contacts-large.csv
gradlew.bat serializationBench # сравнение JSON и бинарного формата (лаб. 3)
```

Для `serializationBench` число записей задаётся свойством `count`:
`gradlew.bat serializationBench -Pcount=50000`.

## Формат CSV

Файл UTF-8, первая строка — заголовок, разделитель полей — точка с запятой `;`.
Один контакт — одна строка. Значения с символом `;` внутри не поддерживаются.

```text
type;name;phone;email;organization;position;internalNumber;note;tags
corporate;Иван Иванов;+79990000000;ivan@example.com;ООО Ромашка;Инженер;123;Важный клиент;работа,важный
emergency;Пожарная служба;101;;МЧС;;;;;
```

| Поле | Значение |
|---|---|
| `type` | `corporate` (корпоративный) или `emergency` (аварийный) |
| `name`, `phone` | обязательные для обоих типов |
| `email`, `organization` | необязательные |
| `position`, `internalNumber` | только для `corporate`; внутренний номер — только цифры |
| `note`, `tags` | новые поля версии 4 (лаб. №4); для старых файлов пустые |

Старые CSV из 7 полей читаются без изменений: `note` и `tags` получают пустые
значения. Новый файл всегда пишется с 9 полями.

Битые строки (неверное число полей, неизвестный тип, нечисловой внутренний номер,
пустые обязательные поля) при загрузке **пропускаются** — одна битая строка не
прерывает загрузку всего файла.

### Большой тестовый файл

`gradlew.bat sampleCsv` создаёт `data/contacts-large.csv` (около 1 МБ):

| Что внутри | Количество |
|---|---|
| корпоративные контакты (тот же генератор, что и кнопка «Сгенерировать») | 10 000 |
| аварийные контакты (read-only, их нельзя создать через GUI) | 10 |
| битые строки: неверное число полей, неизвестный тип, нечисловой номер, пустые обязательные поля, пустая строка | 8 |

При загрузке этого файла приложение сообщает: загружено 10 010 контактов,
пропущено 7 битых строк (пустая строка пропускается молча).
Файл удобен для проверки прогресс-бара, отмены загрузки и визуализации дерева.
Количество можно задать аргументом: `gradlew.bat sampleCsv 50000`.
Файл генерируется и в репозиторий не попадает (см. `.gitignore`).

## Сериализация (лабораторная №3)

Справочник можно сохранять и читать не только в CSV, но и в двух форматах через
общий интерфейс `ru.litper.persistence.serialize.Serializer`:

| Формат | Расширение | Реализация | Особенности |
|---|---|---|---|
| JSON | `.json` | `JsonContactSerializer` (Jackson) | с отступами, удобно читать глазами |
| Бинарный | `.bin` | `BinaryContactSerializer` (`ObjectOutputStream`) | компактнее, поток Java-сериализации с версией в заголовке |

В GUI за это отвечают кнопки **«Экспорт»** и **«Импорт»**: открывается `FileChooser`
с фильтрами `*.json` и `*.bin`, формат определяется по расширению. После импорта
обновляются таблица и визуализация дерева. Операции идут в фоне через `Task`, чтобы
не блокировать интерфейс.

### Модель файла

Перед записью контакты превращаются в плоские записи `ContactRecord` (те же поля, что
и в CSV) и складываются в `ContactData` вместе с версией схемы `schema_version`.

```json
{
  "schema_version" : 3,
  "contacts" : [ {
    "type" : "corporate",
    "name" : "Иван Иванов",
    "phone" : "+79990000000",
    "email" : "ivan@example.com",
    "organization" : "ООО Ромашка",
    "position" : "Инженер",
    "internalNumber" : "123",
    "note" : "Важный клиент",
    "tags" : "работа,важный"
  } ]
}
```

Бинарный файл — поток Java-сериализации (`ObjectOutputStream`). В начале идёт
служебный заголовок `AC ED 00 05`, затем класс `ContactBookFile` с меткой `LITP`,
версией схемы и массивом записей. Метка и версия проверяются в кастомном
`readObject` — чужой или повреждённый файл даёт понятную ошибку
`SerializationException`, а не «мусор» в таблице.

Версия схемы пишется в оба формата. Старое имя поля `schemaVersion` в JSON тоже
принимается, чтобы открывались файлы, созданные до лабораторной №4.

### Сравнение форматов

`gradlew.bat serializationBench` (10 000 контактов, среднее из 5 прогонов):

| Формат | Размер файла | Сохранение | Загрузка |
|---|---|---|---|
| JSON | 2 943 624 байт | 58.78 мс | 98.24 мс |
| бинарный | 1 020 593 байт | 55.23 мс | 54.89 мс |

Выводы (цифры зависят от машины):

* бинарный формат примерно в 2,9 раза компактнее и читается примерно в 1,8 раза
  быстрее, а сохранение по времени сопоставимо: Java-сериализация хранит строки
  без имён полей и форматирования JSON;
* JSON проигрывает в размере, но его можно открыть и прочитать текстовым редактором —
  это важно для отладки и обмена данными;
* оба формата дают одинаковый результат после roundtrip (`load(save(x)) == x`).

## Версионирование и миграции (лабораторная №4)

В контакт добавлены два новых поля: **заметка** (`note`, версия 2) и **теги**
(`tags`, версия 3). Версия схемы хранится в заголовке каждого формата:

| Версия | Что есть | Что добавлено |
|---|---|---|
| 1 | исходные 7 полей | — |
| 2 | + `note` | заметка, по умолчанию `""` |
| 3 | + `tags` | теги, по умолчанию `""` |

Миграция выполняется пошагово (`ru.litper.persistence.migration.ContactMigration`):
v1 → v2 добавляет заметку, v2 → v3 добавляет теги. Каждый шаг — отдельная функция,
поэтому цепочка v1 → v3 переиспользует шаги v1 → v2 и v2 → v3.

При импорте файла старой версии GUI спрашивает:
«Файл версии 1. Мигрировать до 3?» — и показывает, какие поля будут добавлены.
Если пользователь отказывается, текущие данные не меняются. Файл из будущего
(версия больше текущей) и повреждённые записи отклоняются с понятным сообщением.
Если в ходе миграции обнаруживается незаполненное обязательное поле, в ошибке
указывается номер записи.

При экспорте можно выбрать версию схемы:

| Версия | Что теряется |
|---|---|
| 3 | ничего (текущая) |
| 2 | теги |
| 1 | заметки и теги |

Перед сохранением в старую версию GUI предупреждает о потере полей. В JSON
недоступные для выбранной версии поля не пишутся, в бинарном формате перед
сериализацией очищаются (`null`), а при импорте миграция заполняет их `""`.

## REST API (лабораторные №5–6)

Spring Boot-сервер запускается в отдельном проекте `litper-server`
(`ru.litper.server.ServerApp`) на порту `8080`. Клиент `litper-client` не имеет
доступа к хранилищу: все операции он выполняет через HTTP API, а затем
перечитывает снимок данных для таблицы и дерева.

ID контактов — runtime-идентификаторы сервиса. Они не добавляются в CSV/JSON,
поэтому старые файлы и формат лабораторных №3–4 не меняются.

### Endpoints

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/contacts` | фильтры `name`, `organization`, `type`, `phone`, `email`, `note`, `tags` |
| `GET` | `/api/contacts/{id}` | один контакт |
| `POST` | `/api/contacts` | создать, ответ `201` + `Location` |
| `PUT` | `/api/contacts/{id}` | изменить только `Editable`, иначе `422` |
| `DELETE` | `/api/contacts/{id}` | удалить, ответ `204` |
| `GET` | `/api/contacts/search?prefix=иван&limit=50` | автодополнение по префиксу |
| `GET` | `/api/contacts/count?prefix=иван` | число контактов в поддереве |
| `GET` | `/api/contacts/find?name=Иван Иванов` | точный поиск по имени |
| `POST` | `/api/contacts/generate?count=1000&seed=42` | заменить справочник сгенерированным набором |
| `POST` | `/api/contacts/clear` | очистить справочник |
| `DELETE` | `/api/contacts/by-name?name=Иван Иванов` | удалить контакты с точным именем |
| `DELETE` | `/api/contacts/by-prefix?prefix=ив` | удалить всё поддерево по префиксу |
| `POST` | `/api/export?format=json\|bin\|csv&version=3` | файл справочника в ответе |
| `POST` | `/api/import?format=json\|bin\|csv` | импорт из тела запроса, старые версии мигрируются |

Фильтры необязательны и сравниваются без учёта регистра. `limit` ограничен
значением `200`. Дубликатом считается совпадение имени и телефона.

### Ошибки

Все ошибки возвращаются в формате ProblemDetail (RFC 9457) с полями `title`,
`detail`, `status`; ошибки валидации дополнительно содержат массив `errors`.

| Код | Когда |
|---|---|
| `400` | ошибка валидации, некорректный числовой параметр, неизвестный тип/формат, повреждённый файл |
| `404` | контакт с таким ID не найден |
| `409` | дубликат имя+телефон или файл новее текущей версии схемы |
| `422` | `PUT` для read-only `EmergencyContact` |
| `500` | непредвиденная ошибка сервера |

### Примеры curl

```bash
# список и фильтр
curl "http://localhost:8080/api/contacts"
curl "http://localhost:8080/api/contacts?type=corporate&name=иван"

# создание
curl -i -X POST http://localhost:8080/api/contacts \
  -H "Content-Type: application/json" \
  -d '{"type":"corporate","name":"Иван Иванов","phone":"+79990000000",
       "email":"ivan@example.com","organization":"ООО Ромашка",
       "position":"Инженер","internalNumber":"123","note":"","tags":"работа"}'

# изменение
curl -i -X PUT http://localhost:8080/api/contacts/1 \
  -H "Content-Type: application/json" \
  -d '{"type":"corporate","name":"Иван Петров","phone":"+79990000001",
       "position":"Ведущий инженер","internalNumber":"456"}'

# поиск и подсчёт
curl "http://localhost:8080/api/contacts/search?prefix=иван&limit=10"
curl "http://localhost:8080/api/contacts/count?prefix=иван"

# удаление
curl -i -X DELETE http://localhost:8080/api/contacts/1

# экспорт и импорт
curl -X POST "http://localhost:8080/api/export?format=json" -o contacts.json
curl -X POST "http://localhost:8080/api/import?format=json" \
  -H "Content-Type: application/octet-stream" --data-binary "@contacts.json"
```

Клиент `litper-client` выполняет эти же запросы через `ApiClient` и после
изменения перечитывает снимок данных. Кнопка «Обновить» нужна, если данные
изменил другой клиент или внешний запрос.

## Модель

```text
Contact
├── EmergencyContact       // read-only, появляется только из CSV
└── CorporateContact       // implements Editable (должность, внутренний номер)
```

`Editable` — контракт «сущность можно изменять» с методом `validate()`.
Кнопка «Изменить» в GUI активна только для `CorporateContact`; через «Добавить»
создаётся только корпоративный контакт. Поля `note` и `tags` есть у всех
контактов, но редактировать их через диалог можно только у корпоративного типа.

## Префиксное дерево (Trie)

Ключ индексации — имя контакта в нижнем регистре (`ru.litper.service.ContactService`),
поэтому поиск не зависит от регистра. Дерево реализовано на собственных узлах
и массивах: коллекции `java.util` как хранилище не используются.

```text
          (root)
          /    \
         м      н
        / \     / \
      а    р   а    а
      |    |   |    |
      р    к   т    т
      |    |   |    |
      и    (МАРК)  ш(наталья)
      / \
  н(марина) я(мария)
```

* `TrieNode` — символ, дети в **отсортированном массиве** (бинарный поиск),
  значения терминального узла (имена могут совпадать) и счётчик контактов
  в поддереве.
* `Trie<T>` — дженерики: в конструктор передаются класс элемента и `KeyExtractor`
  (как получить ключ из значения).
* Снаружи отдаются только геттеры: изменить узел из GUI нельзя.
* Каждая операция запоминает посещённые узлы (`lastTrace()`) и текст операции
  (`lastOperation()`) — по ним визуализация подсвечивает пройденный путь.

### Асимптотика

Обозначения: `L` — длина имени, `σ` — размер алфавита, `N` — число контактов,
`V` — число узлов, `K` — размер результата (поддерева/найденных контактов).

| Операция | O(...) | Обоснование |
|---|---|---|
| `insert` | O(L·log σ) | спуск по L символам, в узле бинарный поиск ребёнка; массив детей при вставке сдвигается |
| `findAll`, `findNode`, `contains` | O(L·log σ) | тот же спуск |
| `remove`, `removeKey` | O(L·log σ) | спуск + удаление из узла + подрезка пустых узлов (их ≤ L) |
| `removePrefix` | O(L·log σ + K) | спуск + отсоединение поддерева размера K |
| `autocomplete` | O(L·log σ + K) | спуск по префиксу + обход поддерева и сбор K контактов |
| `countByPrefix` | O(L·log σ) | спуск + чтение счётчика в узле (O(1)) |
| `toArray` | O(V + N) | обход всех узлов, дети уже отсортированы |

Сортировка детей даёт алфавитный порядок обхода «бесплатно» — поэтому
`toArray()` не требует сортировки.

### Сравнение с `java.util`

`gradlew.bat benchmark` (среднее из 5 прогонов, тот же набор ключей):

| Операция | N | своё Trie | `TreeMap` | отношение |
|---|---|---|---|---|
| вставка | 10⁴ | 17.10 мс | 5.52 мс | 3.10x |
| поиск по имени | 10⁴ | 0.11 мс | 0.04 мс | 2.75x |
| автодополнение (50) | 10⁴ | 0.19 мс | 0.35 мс | 0.55x |
| подсчёт по префиксу | 10⁴ | 0.08 мс | 0.63 мс | 0.12x |
| удаление | 10⁴ | 0.07 мс | 0.02 мс | 3.52x |
| вставка | 10⁵ | 37.46 мс | 16.83 мс | 2.23x |
| поиск по имени | 10⁵ | 0.06 мс | 0.03 мс | 1.80x |
| автодополнение (50) | 10⁵ | 0.20 мс | 0.11 мс | 1.80x |
| подсчёт по префиксу | 10⁵ | 0.03 мс | 0.10 мс | 0.31x |
| удаление | 10⁵ | 0.04 мс | 0.02 мс | 1.58x |

Выводы (цифры зависят от машины, сравнение — на одном наборе ключей):

* `TreeMap` быстрее на точных операциях: у него готовое красно-чёрное дерево,
  а у нас поиск ребёнка в массиве плюс поддержка счётчиков;
* своё дерево выигрывает на префиксных запросах, особенно на подсчёте:
  ответ берётся из счётчика за O(1), а `TreeMap` вынужден считать диапазон;
* `TreeMap` хранит один ключ — контакты с одинаковым именем схлопываются,
  Trie держит все значения в терминальном узле.

### Конкурентный доступ

`gradlew.bat raceDemo` — два потока по 10 000 увеличений:

```text
Без синхронизации: ожидалось 20000, получено 13989 — потеряно обновлений: 6011
Trie с synchronized: ожидалось 20000, получено 20000
Гонки нет: критическая секция защищена.
```

Защита в проекте:

* все публичные операции `Trie` объявлены `synchronized`;
* читающие методы возвращают **копии** (`toArray()`, `lastTrace()`), поэтому
  GUI-поток никогда не видит «наполовину перестроенную» структуру;
* тяжёлые операции (загрузка CSV, генерация) идут в фоновом потоке через
  `javafx.concurrent.Task`, интерфейс обновляется через `setOnSucceeded`.

## Лабораторная работа №6 (REST-клиент)

Клиент вынесен в отдельный проект `litper-client` и работает с сервером
`litper-server` только через HTTP API (`java.net.http.HttpClient`,
JSON через Jackson). Прямого доступа к `ContactService` или хранилищу у клиента нет.

### Запуск

1. В папке `litper-server`: `gradlew.bat serverRun`
2. В папке `litper-client`: `gradlew.bat clientRun`

По умолчанию клиент подключается к `http://localhost:8080`. Сервер должен быть
запущен до выполнения операций в клиенте.

### Возможности клиента

- Интерфейс сохранён как в лабораторной №5: таблица, панель Trie, кнопки
  «Загрузить CSV», «Сохранить CSV», «Обновить», «Экспорт», «Импорт»,
  «Добавить», «Изменить», «Сгенерировать», «Очистить», поиск и удаление
  по имени/префиксу.
- Все операции изменения выполняются через REST API: CRUD, генерация, очистка,
  удаление по имени/префиксу, экспорт и импорт (`csv`/`json`/`bin`).
- Поиск по префиксу/имени и подсчёт также доступны через REST API; клиент дополнительно
  строит локальное отражение Trie по снимку данных для отрисовки на `Canvas`.
  Источник истины — сервер.
- Все сетевые операции выполняются в фоне (`Task`) с индикатором и кнопкой
  отмены, интерфейс не блокируется.

### Обработка сетевых ошибок

- Недоступный сервер / ошибка соединения: показывается понятное сообщение с
  подсказкой проверить запуск `serverRun`.
- Ошибки HTTP обрабатываются по ответу ProblemDetail (`400`, `404`, `409`,
  `422`, `500`) и показываются пользователю в диалоге.
- Некорректный или неожиданный ответ сервера обрабатывается как ошибка клиента
  без падения приложения.
- Это поведение покрыто тестом `HttpApiClientTest` в `litper-client`.
