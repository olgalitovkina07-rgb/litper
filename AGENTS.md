# AGENTS.md — инструкции для OpenCode

## Контекст проекта

Это учебный проект на Java по лабораторной работе №1 «Разработка модели данных».
Нужно выполнить **вариант 4 — «Справочник контактов»** по приложенной методичке `instruction.md`.

Вариант 4:
- базовая сущность: `Contact`
  - имя
  - телефон
  - e-mail
  - организация
- read-only сущность: `EmergencyContact`
- редактируемая сущность: `CorporateContact`
  - должность
  - внутренний номер
- структура данных для последующей лабораторной №2: Trie по имени. **В лабораторной №1 собственный Trie реализовывать не нужно**, если это прямо не требуется текущим заданием.

## Технологии

- Java 21 LTS
- Gradle Kotlin DSL
- JavaFX
- IntelliJ IDEA
- JUnit 5 можно подключить для будущих лабораторных, но не усложнять текущую лабораторную без необходимости.

## Главное правило

Методичка `instruction.md` является главным источником требований. Перед реализацией сверяйся с ней и не добавляй функции, которые противоречат заданию.

Для лабораторной №1 обязательны:
1. Иерархия минимум из трёх типов.
2. Интерфейс `Editable`.
3. CSV-загрузка с пропуском битых строк.
4. GUI:
   - отображение контактов;
   - загрузка из CSV;
   - сохранение в CSV;
   - редактирование только `Editable`;
   - добавление сущности;
   - диалоги ошибок.
5. Для read-only объектов кнопка «Изменить» должна быть недоступна.
6. Через «Добавить» разрешено создавать только редактируемые типы.
7. Read-only-типы появляются из файла.
8. Не делать приложение «god object»: GUI не должен содержать всю бизнес-логику.
9. Не проглатывать исключения.
10. Не использовать магические строки и числа там, где уместны константы или enum.
11. Не делать операции, которые могут выполняться долго, непосредственно в JavaFX UI-потоке.

## Модель

Использовать наследование:

```text
Contact
├── EmergencyContact       // read-only
└── CorporateContact       // implements Editable
```

`Editable` — контракт возможности изменения. Предпочтительно использовать вариант с методом `validate()`, если это не усложняет проект неоправданно:

```java
public interface Editable {
    List<String> validate();
}
```

`CorporateContact` должен реализовывать `Editable`.

`EmergencyContact` не должен реализовывать `Editable`.

Не использовать `Editable` как родительский класс.

## CSV

Нужен понятный собственный формат. Например:

```text
type;name;phone;email;organization;position;internalNumber
corporate;Иван Иванов;+79990000000;ivan@example.com;ООО Ромашка;Инженер;123
emergency;Пожарная служба;101;;МЧС;;
```

Требования:
- первая строка — заголовок;
- разделитель `;`;
- некорректные строки пропускать;
- ошибка одной строки не должна прекращать загрузку всего файла;
- при ошибке чтения файла показывать понятный диалог;
- формат должен быть описан в `README.md`.

Если выбран другой CSV-формат, зафиксировать его в README и придерживаться его во всех местах.

## GUI

Интерфейс должен быть простым и демонстрировать требования лабораторной.

Минимальный набор:
- таблица контактов;
- кнопка «Загрузить CSV»;
- кнопка «Сохранить CSV»;
- кнопка «Добавить»;
- кнопка «Изменить»;
- диалоги для ввода/редактирования;
- сообщения об ошибках.

Логика доступности:
- если выбран `CorporateContact` → «Изменить» доступна;
- если выбран `EmergencyContact` → «Изменить» заблокирована;
- «Добавить» не должна создавать `EmergencyContact`.

Можно добавить выбор типа при добавлении, но создавать через GUI только `CorporateContact`.

## Архитектура

Стараться разделять ответственность:

- `model` — сущности и интерфейс;
- `persistence` — CSV;
- `service` — операции над контактами и правила;
- `gui` — JavaFX и отображение.

Контроллер GUI не должен самостоятельно разбирать CSV и содержать всю предметную логику.

## Стиль кода

- Код должен быть понятным студенту, без излишней сложности.
- Не использовать сторонние библиотеки без необходимости.
- Не добавлять Lombok и другие инструменты только ради сокращения нескольких строк.
- Не использовать `catch (Exception e) {}` без обработки.
- Имена классов/методов/переменных — понятные.
- Публичные методы и важные решения можно кратко документировать.
- Не делать огромные методы.
- Не менять требования методички ради «красивой архитектуры».

## Работа агента

Перед изменениями:
1. Прочитать `instruction.md`.
2. Прочитать `PLAN.md`.
3. Проверить текущее состояние репозитория.
4. Не переписывать уже работающий код без причины.

После каждого существенного этапа:
1. Собрать проект.
2. Запустить тесты, если они есть.
3. Исправить ошибки компиляции.
4. Проверить соответствие пунктам методички.

В конце:
- проект должен собираться;
- приложение должно запускаться;
- основные сценарии лабораторной должны работать;
- README должен содержать инструкцию запуска и формат CSV;
- не удалять `instruction.md`, `AGENTS.md` или `PLAN.md`.
