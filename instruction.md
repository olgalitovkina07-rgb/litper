# Программирование на Java

## Методические указания и задания к лабораторным работам

> **Формат курса — сквозной проект.** Все шесть лабораторных развивают одно приложение: от модели данных до распределённого клиент-серверного решения. Вариант выдаётся один раз и закрепляется за бригадой на **все** лабораторные работы.
>
> Бригада может состоять не более чем из 2 человек. Соответственно это либо 1 человек, либо 2 человека. **Больше - нельзя.**
> 
> **Стек - Java (можно Kotlin)**
> Рекомендуемые версии: Java 21 LTS; Java 25

### Технологический стек

| Компонент | Требование |
|---|---|
| Платформа | Java 21 LTS (минимум), рекомендуется Java 25 LTS. JDK — любой вендор (Temurin и т. п.) |
| IDE | **IntelliJ IDEA** (Community или Ultimate) / [GigaIDE](https://gitverse.ru/features/gigaide/) |
| Сборка | Gradle (Kotlin DSL) или Maven, toolchains; GUI подключается плагином/зависимостями OpenJFX — в составе JDK его нет |
| Тестирование | JUnit 5 |
| GUI | JavaFX (OpenJFX 21+) / Compose |
| Сервер | Spring Boot 3.x |
| Сериализация | `java.io.Serializable` и/или собственный бинарный формат; Protocol Buffers (proto3); Jackson JSON |
| Сеть | `java.net.http.HttpClient` / Ktor |

### Уровни выполнения

Каждый уровень предполагает выполненный каждый пункт задание качественно, в котором вы разбираетесь на 100% и готовы ответить на вопрос по коду самостоятельно в режиме реального времени.

| Уровень | Оценка | Смысл |
|---|---|---|
| Минимум | удовлетворительно | Базовый работающий функционал; без него лабораторная не сдаётся |
| Среднее | хорошо | Инженерное качество: валидация, обработка ошибок, полные тесты, замеры |
| Максимум | отлично | Продвинутые техники, автоматизация, исследования и сравнения в отчёте |

Уровни **кумулятивны**: среднее включает весь минимум, максимум — всё среднее.

### Отчёт, защита, сдача

Отчёт (DOCX) по каждой лабораторной:

1. Титульный лист.
2. Содержание/оглавление.
3. Цель, вариант, ТЗ.
4. Ход работы: ФРАГМЕНТЫ кода и пояснения с описанием ключевых решений.
5. Демонстрация работы: скриншоты реализации и примеры показывающие работоспособность программы.
6. Выводы/заключение.

Приложение с вставкой исходного кода **не нужно**. При сдаче отчёта с таким приложением это приведёт к снижению полученных баллов на 20%.

Защита — демонстрация работающего приложения и ответы на вопросы.
Копирование кода между студентами — смена варианта и обнуления всех существующих работ.

### Типичные анти-паттерны (снижают оценку)

- Вся логика в контроллере GUI / в контроллере REST («god object»).
- Проглатывание исключений (`catch (Exception e) {}`).
- Магические числа и строки вместо констант/`enum`.
- Тесты, проверяющие «всё и сразу» вместо одного поведения.
- Блокировка GUI-потока любой операцией дольше 100 мс.

Дополнительные сущности:

_Структура данных_

AVL-дерево (ключ — дата-время)

<details>

То же BST (см. вариант 1), но после каждой вставки/удаления проверяется баланс: высоты поддеревьев отличаются не более чем на 1. Нарушение лечится малыми поворотами (LL, RR, LR, RL).

```text
вставка 10:10 в правое поддерево → дисбаланс у 10:00
                [10:00]  balance = -2
               /         \
        [09:30]         [10:00]
                          \
                         [10:10]

малый левый поворот (RR):
                [10:05]
               /       \
        [10:00]        [10:10]
       /
  [09:30]
```

📖 [Википедия — AVL-дерево](https://ru.wikipedia.org/wiki/AVL-дерево), [VisuAlgo — AVL](https://visualgo.net/en/avl)
  
</details>

_Основная сущность_
Товар

_Структура данных_

B-дерево порядка 4 (ключ — артикул)

<details>

Многоярусное дерево: каждый узел хранит до 3 ключей и до 4 детей; все листья на одном уровне — дерево растёт «вверх» через расщепление полных узлов.

```text

                    /    │     \
        [100│200│300]  [600│700]  [950│980│990]          ← все листья на h=1

вставка 400 в [100│200│300] → узел полон → расщепление:
                     [ 300 │ 500 │ 900 ]
                    /     │      │    \
              [100│200] [400] [600│700] [950│980│990]
```

📖 [Википедия — B-дерево](https://ru.wikipedia.org/wiki/B-дерево), [Визуализатор USFCA](https://www.cs.usfca.edu/~galles/visualization/BTree.html)
  
</details>

**4. Справочник контактов**

_Основная сущность_
Контакт
- имя
- телефон
- e-mail
- организация

Дополнительные сущности:
- Аварийный контакт (read-only)
- Корпоративный контакт
  - должность
  - внутренний номер

_Структура данных_

Префиксное дерево — Trie (по имени)

<details>

Каждый узел — символ; слово читается по пути от корня. Автодополнение — спуск по префиксу + сбор всех поддеревьев ниже найденного узла.

```text
        (root)
        /    \
       а      м
      / \      \
    н    р      а
    |    |      |
    н    я      р
    |           |
    а           и
    |           |
  [НАТА]      [МАРИЯ]        [] — терминальный узел

автодополнение "ма": спустились по м→а → собираем [МАРИЯ]
```

📖 [Википедия — Префиксное дерево](https://ru.wikipedia.org/wiki/Префиксное_дерево), [Визуализатор USFCA](https://www.cs.usfca.edu/~galles/visualization/RadixTree.html)
  
</details>

_Дополнительные операции_

**5. Склад**

_Основная сущность_
Партия
- артикул
- название
- количество
- ячейка
- дата завоза

Дополнительные сущности:
- Архивная партия (read-only)
- Импортная партия
  - страна
  - таможенный код

_Структура данных_

Хеш-таблица с открытой адресацией (ключ — артикул, линейное пробирование)

<details>

Массив ячеек; индекс = hash(key) % capacity. Если ячейка занята — сдвиг на шаг вправо, пока не найдётся свободная. При заполнении выше порога — рехеш: удвоение размера и переселение всех записей.

```text
index:   0        1        2        3        4        5
       ┌────────┬────────┬────────┬────────┬────────┬────────┐
       │  91005 │ DELETED│  91011 │  91117 │  free  │  91002 │
       └────────┴────────┴────────┴────────┴────────┴────────┘

put(91117): h(91117)=2 → занято(91011) → проба+1 → 3 свободно → пишем
                                        ^^ 2 пробы (статистика в отчёт)

load factor 0.75 → рехеш: capacity 6 → 12, все элементы переселятся
```

📖 [Википедия — Хеш-таблица](https://ru.wikipedia.org/wiki/Хеш-таблица), [Визуализатор USFCA](https://www.cs.usfca.edu/~galles/visualization/OpenHash.html)
  
</details>

_Дополнительные операции_

- put/get/delete со статистикой проб
- Автоматический рехеш при заполнении

**6. Электронная очередь поликлиники**

_Основная сущность_
Талон
- № карты
- ФИО
- кабинет
- срочность (0–3)
- время взятия

Дополнительные сущности:
- Закрытый талон (read-only)
- Талон на дому
  - адрес

_Структура данных_

Двоичная min-куча (компаратор: срочность, затем время взятия)

<details>

Полное дерево, хранящееся прямо в массиве: приоритет родителя ≤ приоритетов детей. Вставка — «всплытие» вверх, извлечение минимума — «погружение» вниз.

```text
массив: [ A1 │ B3 │ A2 │ C5 │ B4 │ D3 │ C6 ]
индекс:   0    1    2    3    4    5    6
             parent i → (i-1)/2;  children i → 2i+1, 2i+2

дерево (срочность в узле):
                (1,A1)
              /        \
          (3,B3)       (2,A2)
          /     \       /    \
      (5,C5)  (4,B4) (3,D3) (6,C6)

вставка (0, C9): в конец → всплытие до корня
      (0,C9) → (1,A1) → (3,B3) → (5,C5) → конец
```

📖 [Википедия — Двоичная куча](https://ru.wikipedia.org/wiki/Двоичная_куча), [VisuAlgo — Binary Heap](https://visualgo.net/en/heap)
  
</details>

_Дополнительные операции_

**7. Социальная сеть**

_Основная сущность_
Профиль
- id
- имя
- город
- год рождения
- связь «дружба»: пара id, «сила» связи

Дополнительные сущности:
- Удалённый профиль (read-only)
- Сообщество
  - администратор

_Структура данных_

Граф: вершины — профили, рёбра — дружба. Списки смежности разрешены, если узел списка — собственная структура (не `java.util`-список)

<details>

Вершины + рёбра; соседи хранятся в списках смежности. BFS (обход «в ширину» по слоям) даёт кратчайшую цепочку знакомств; Дейкстра учитывает вес ребра — «силу» связи.

```text
        Аня ──── Борис ──── Вера
         │        │          │
        Глеб ────√          Дима

   adjacency:
     Аня   → [Борис, Глеб]
     Борис → [Аня, Вера, Глеб]
     Вера  → [Борис, Дима]
     Глеб  → [Аня, Борис]
     Дима  → [Вера]

BFS Аня→Дима: Аня → Борис → Вера → Дима   (цепочка длины 3)
```

📖 [Википедия — Представление графа](https://ru.wikipedia.org/wiki/Список_рёбер#Списки_смежности), [Визуализатор USFCA](https://www.cs.usfca.edu/~galles/visualization/BFS.html)
  
</details>

_Дополнительные операции_

- Кратчайшая цепочка знакомств (BFS)

**8. Карта мест (POI)**

_Основная сущность_
Место
- id
- название
- категория
- широта
- долгота

Дополнительные сущности:
- Место «на модерации» (read-only)
- Сетевое место
  - сайт
  - телефон

_Структура данных_

k-d дерево по (широта, долгота)

<details>

Дерево, где сравнение идёт поочерёдно по осям: чётный уровень — широта, нечётный — долгота. Каждое разбиение «режет» плоскость — красивая визуализация областями. Поиск области — проверка пересечения прямоугольника поддерева с запросом.

```text
корень — x:          [ (50,30) ]
                    /            \
   y-уровень:   [ (20,60) ]     [ (70,20) ]
                /       \            \
x-уровень:  [(10,40)] [(40,70)]   [(80,50)]

плоскость (альтерн. разрезы):
  ┌───────────────────────┐
  │          │ (50,30)    │      вертикальный разрез по x=50
  │ (20,60)──┼──(70,20)   │      затем горизонтальные по y
  │    │     │      │     │
  │(10,40) (40,70) (80,50) │
  └───────────────────────┘
```

📖 [Википедия — k-d дерево](https://en.wikipedia.org/wiki/K-d_tree)
  
</details>

_Дополнительные операции_

- Все точки в прямоугольной области

**9. Таск-трекер**

_Основная сущность_
Задача
- id
- название
- исполнитель
- срок
- важность (1–10)

Дополнительные сущности:
- Задача в архиве (read-only)
- Срочная задача
  - дежурный

_Структура данных_

Декартово дерево — treap (ключ — срок, приоритет кучи — важность)

<details>

Гибрид BST и кучи: по ключу (срок) — дерево поиска, по приоритету (важность) — куча. Рекомендуемая реализация — через split/merge, а не вращения.

```text
ключ(срок)=число, приоритет(важность)=буква (A — самый важный)
по сроку: слева меньше; по важности: родитель важнее (буква раньше)

              (10 мар, A)
             /           \
       (05 мар, C)     (20 мар, B)
       /         \
(01 мар, D)  (07 мар, E)

merge(A, B): всё с ключом < ключа(B) — в левую часть; корень = важнейший
split(T, дедлайн 08 мар): { 01, 05, 07 } | { 10, 20 }
```

📖 [Хабр — Декартово дерево (секретная информация о декартовых деревьях)](https://habr.com/ru/articles/44353/), [Wikipedia — Treap](https://en.wikipedia.org/wiki/Treap)
  
</details>

_Дополнительные операции_

- Задачи в интервале сроков
- N самых важных

**10. Бронирование переговорных**

_Основная сущность_
Бронь
- id
- комната
- сотрудник
- начало
- конец

Дополнительные сущности:
- Прошедшая бронь (read-only)
- Регулярная бронь
  - дни недели

_Структура данных_

Дерево по началу брони (ключ — «начало»; пересечение проверяется при обходе диапазона)

<details>

Обычное дерево поиска по началу брони, пересечения ищутся при обходе нужного диапазона. Дерево интервалов (на максимум) добавляет в узел аугментацию `max_end` — максимум концов поддерева, что позволяет отсекать ветви.

```text
          [09:00 ─ 10:30]  max_end=13:00        ← в узле храним max концов поддерева
         /                 \
 [08:00─09:30]          [11:00 ─ 13:00]  max_end=13:00
      max_end=09:30

запрос: пересекается ли [10:45 ─ 11:30]?
  корень: 10:45 < 10:30 ? нет → может пересекаться справа
  правый: 11:00 ≤ 11:30 и 10:45 ≤ 13:00 → ПЕРЕСЕЧЕНИЕ ✔ (конфликт комнаты)

отсечение: если max_end(лев. поддерева) < 10:45 → левое пропускаем целиком
```

📖 [Wikipedia — Interval tree](https://en.wikipedia.org/wiki/Interval_tree)
  
</details>

_Дополнительные операции_

- Брони, пересекающиеся с интервалом
- Проверка конфликта комнаты

Примечания.

- Семантика read-only-типов — «архивные/закрытые» записи: они видны в GUI, но редактирование запрещено.
- Синтетические производные типы из списка «Дополнительные сущности» можно дополнять своими, если сохраняются обязательные три типа: базовый, read-only, редактируемый с новыми полями.

## Лабораторная работа № 1. «Разработка модели данных»

### Задание

1. Реализовать сущности согласно варианту в ООП паттернах. Минимум три типа из «Дополнительных сущностей» (базовый, read-only, редактируемый с дополнительными полями).
2. Добавить интерфейс `Editable`. Маркерный или с методами. Кнопка «Изменить» в GUI доступна только для объектов, реализующих `Editable`. Через «Добавить» можно создать только редактируемые типы; read-only-типы появляются только из файла.
3. Загрузка данных из файла CSV. Битые строки пропускаются.
4. Реализация GUI:
  - отображение элемента(ов)
  - загрузить из CSV
  - сохранить в CSV
  - редактирование сущности (не read-only)
  - добавление сущности
  - предусмотреть диалоги с ошибками

### Детали реализации

**1. Интерфейс `Editable`** — контракт «сущность можно менять». Может быть маркером (без методов) или нести методы, например проверку полей:

```java
public interface Editable {
    /** @return список ошибок; пустой список = данные корректны */
    List<String> validate();
}
```

Кнопка «Изменить» в GUI проверяет `entity instanceof Editable` и блокируется для read-only-типов. Решение «маркер или с методами» принимаете сами и обосновываете в отчёте.

📖 [Metanit — Интерфейсы](https://metanit.com/java/tutorial/3.7.php) · [Metanit — Классы Records](https://metanit.com/java/tutorial/3.18.php) (удобны для неизменяемых read-only-типов)

**2. Наследование** — базовая сущность, от которой наследуются производные с новыми полями:

```java
public class Book {                          // базовый тип
    protected String isbn;
    protected String title;
    // конструктор, геттеры/сеттеры
}

public class Textbook extends Book implements Editable {   // редактируемый, + новые поля
    private int course;
    private int printRun;
    @Override public List<String> validate() { /* проверка полей */ return List.of(); }
}
```

Это аналог шаблонов C++, но проверка происходит на этапе компиляции, а примитивы (`int`) нужно упаковывать в обёртки (`Integer`). Ограничение `K extends Comparable<K>` требует от ключа умения сравнивать себя (`compareTo`) — вместо `operator<` из C++.

**1. Какой сериализации хотим:** несколько реализаций одного контракта (интерфейс выше) — GUI и тесты работают через `Serializer`, не зная, что внутри: JSON, бинарный формат или что-то ещё. Пример реализации JSON-варианта на Jackson:

```java
public final class JsonBookSerializer implements Serializer<BookData> {
    @Override public String format() { return "json"; }

    @Override public void save(BookData data, Path file) throws IOException {
        new ObjectMapper().writeValue(file.toFile(), data);
    }
    @Override public BookData load(Path file) throws IOException {
        return new ObjectMapper().readValue(file.toFile(), BookData.class);
    }
}
```

Roundtrip-контракт: `load(save(x))` обязан вернуть данные, равные `x` — это главный тест сериализации.

**2. `Serializable` и версионирование.** Бинарный формат «из JDK»: класс реализует маркер-интерфейс `java.io.Serializable`, а JDK сама записывает объект в поток байтов. Поле `serialVersionUID` — «паспорт версии» класса: если при чтении версия класса не совпала с записанной, получится `InvalidClassException`. Именно поэтому `serialVersionUID` — первая, примитивная форма версионирования формата (пригодится в лаб. 4).

```java

    private static final long serialVersionUID = 1L;   // версия схемы
    private String isbn;
    private String title;
}
```

### Детали реализации

**1. Что такое миграция.** Миграция — автоматическое преобразование данных из старой версии формата в текущую при чтении файла. Приложение версии N умеет открывать файлы версий 1…N: смотрит `schema_version` в файле и применяет цепочку пошаговых преобразований. Каждый шаг — маленькая изолированная функция «данные версии k → данные версии k+1»: так шаги можно тестировать отдельно и переиспользовать (v1→v3 = v1→v2 + v2→v3).

**2. Скелет шага миграции** — новое поле с заполнением по умолчанию:

```java
/** v1 → v2: добавили поле rating; для старых записей — значение по умолчанию */
public final class MigrationV1toV2 {
    public static Map<String, Object> migrate(Map<String, Object> record) {
        record.putIfAbsent("rating", 0.0);      // НЕ null — конкретное значение
        record.put("schema_version", 2);
        return record;
    }
}
```

Представление записи как `Map<String, Object>` (или JSON-дерево Jackson) удобно: поля можно добавлять/переименовывать независимо от класса модели, а сам класс модели меняется один раз, в текущей версии. Реестр миграций — список шагов, применяемых по порядку, пока версия записи не сравняется с текущей.

**3. Пример теста миграции** — на фикстуре (эталонном файле версии 1 в `src/test/resources/`):

```java
@Test
void migrates_v1_file_and_fills_default_rating() {
    BookData v1 = loadFixture("books-v1.json");          // schema_version = 1

    BookData v2 = new MigrationV1toV2().apply(v1);

    assertEquals(2, v2.schemaVersion);
    assertEquals(0.0, v2.books.get(0).rating);           // дефолт, не null
    assertEquals(3, v2.books.size());                    // записи не потерялись
}
```

   - `GET /api/{entities}/{id}`;
   - `POST /api/{entities}` → `201` + `Location`;
   - `PUT /api/{entities}/{id}` — **только для `Editable`-типов**, иначе `422`;
   - `DELETE /api/{entities}/{id}`;
   - дополнительные операции варианта (лаб. 2) как под-ресурсы: `/search?prefix=…`, `/range?from=…&to=…`, `/nearest?lat=…&lon=…`, `/path?from=…&to=…` и т. п.;
   - `POST /api/store/swap?structure=…` — переключение используемой структуры данных на лету (если у вас несколько реализаций структуры из лаб. 2; иначе ручку можно не делать — на оценку не влияет);
   - `POST /api/export?format=json|bin`, `POST /api/import` — сериализация из лаб. 3 как сервис.
4. **Ошибки.** Единый формат ProblemDetail (RFC 9457): `400` — ошибка валидации, `404` — нет записи, `409` — дубликат ключа/конфликт, `422` — попытка изменить не-`Editable` запись; доменные исключения (включая `VERSION_TOO_NEW` из лаб. 4) маппятся через `@ExceptionHandler`.

### Детали реализации

**1. Запуск Spring и первый GET.** Проще всего создать проект через [Spring Initializr](https://start.spring.io/) (зависимость Spring Web), затем объявить контроллер:

```java
@RestController
public class BookController {
    private final BookService service;                 // бин с бизнес-логикой

    public BookController(BookService service) { this.service = service; }

    @GetMapping("/api/books")
    public List<BookDto> all() { return service.findAll(); }

    @GetMapping("/api/books/{isbn}")
    public BookDto one(@PathVariable String isbn) { return service.findByKey(isbn); }
}
```

Запуск — `./gradlew bootRun` (или кнопкой Run в IDEA на классе с `@SpringBootApplication`).

📖 [Spring — Building an Application with Spring Boot](https://spring.io/guides/gs/spring-boot) · [Spring — Building a RESTful Web Service](https://spring.io/guides/gs/rest-service)

**2. Проверка в браузере.** GET-запрос открывается прямо в браузере: `http://localhost:8080/api/books` — увидите JSON-ответ. Это самый быстрый способ проверить ручку чтения.

**3. POST и его проверка.** POST меняет состояние, браузером его не отправить — используйте `curl`:

```bash
curl -X POST http://localhost:8080/api/books \
     -H "Content-Type: application/json" \
     -d '{"isbn":"978-5-17","title":"Мартин Иден","year":1909}' -i
```

Ожидаемый ответ: `HTTP/1.1 201 Created` и заголовок `Location: /api/books/978-5-17`. Повторный `GET` по этому адресу возвращает созданную запись.

**4. GUI в том же процессе.** JavaFX-приложение может поднять Spring-контекст в `Application#init()` (этот поток без UI, Spring там разрешён), а в `start()` достать бины `getBean` и вызывать `Service` напрямую, минуя HTTP. Для актуализации данных достаточно кнопки «Обновить» (перечитать данные из сервиса) — либо слушателей изменений сервиса.

```java
public class App extends Application {
    private ConfigurableApplicationContext spring;

    @Override public void init() {
        spring = new SpringApplicationBuilder(ServerApp.class).run();
    }
    @Override public void start(Stage stage) {
        var service = spring.getBean(BookService.class);
        // контроллеры GUI читают/пишут через service; кнопка «Обновить» — service.findAll()
    }
}
```

**5. Архитектура.** Слои Spring-приложения: `controller` принимает HTTP и возвращает DTO (без бизнес-логики), `service` хранит валидацию и бизнес-операции, `store` — ваша структура данных как singleton-бин. Зависимости направлены вниз: контроллер знает сервис, сервис — хранилище, и никогда наоборот.

```java
@Service
public class BookService {
    private final EntityStore<String, Book> store;     // бин-хранилище (ваша структура)
    public BookService(EntityStore<String, Book> store) { this.store = store; }
    public List<Book> findAll() { /* ... */ }
    public Book add(BookDto dto) { /* валидация + store.add */ }
}
```

## Лабораторная работа № 6. «REST-клиент»

### Задание

1. Разделить клиент и сервер. Теперь клиент находится в отдельном приложении и взаимодействует с сервером через API.

### Детали реализации

**1. Базовый сетевой запрос.** Стандартный `java.net.http.HttpClient`: клиент создаётся один раз, запрос собирается билдером, ответ читается как строка:

```java
HttpClient http = HttpClient.newHttpClient();

HttpRequest request = HttpRequest.newBuilder()
        .uri(URI.create("http://localhost:8080/api/books"))
        .GET()
        .build();

HttpResponse<String> response = http.send(request, HttpResponse.BodyHandlers.ofString());
String json = response.body();            // 200 + JSON со списком книг
```

POST отличается телом и заголовком: `.POST(HttpRequest.BodyPublishers.ofString(json))` + `.header("Content-Type", "application/json")`.

📖 [JavaRush — Руководство по HTTP-клиенту Java](https://javarush.com/groups/posts/rukovodstvo-po-http-klientu-java) · [Oracle — HttpClient (javadoc, Java SE 21)](https://docs.oracle.com/en/java/javase/21/docs/api/java.net.http/java/net/http/HttpClient.html)

**2. Слой API-клиента и DTO.** Сетевые вызовы прячутся за интерфейс, а GUI работает с объектами, а не с JSON-строками:

```java
public interface ApiClient {
    List<BookDto> findAll();                            // GET /api/books
    Optional<BookDto> findByKey(String isbn);           // GET /api/books/{id}
    BookDto create(BookDto dto);                        // POST /api/books
    void delete(String isbn);                           // DELETE /api/books/{id}
}

public record BookDto(String isbn, String title, int year) { }   // DTO: record для переноса данных
```

**DTO (Data Transfer Object)** — простой класс-носитель данных между клиентом и сервером: он повторяет формат сетевого ответа, но не содержит логики. JSON-ответ разбирается в DTO тем же Jackson, что и в лаб. 3. GUI зависит от `ApiClient`, а не от HTTP-деталей — так его можно тестировать без сервера.

📖 [Martin Fowler — Data Transfer Object](https://martinfowler.com/eaaCatalog/dataTransferObject.html) · [freeCodeCamp — What are DTOs in Java](https://www.freecodecamp.org/news/what-are-dtos-java/) · [Jenkov — Jackson ObjectMapper](https://jenkov.com/tutorials/java-json/jackson-objectmapper.html)

**3. Визуализация по данным из экспорта.** Структура целиком живёт на сервере, но клиент может восстановить её вид: держите на сервере ручку, отдающую содержимое структуры (например, `GET /api/books/export` — полный список или JSON-снимок структуры). Клиент по этому снимку отрисовывает панель: строит локальное «отражение» структуры (те же узлы и связи) и рисует её на Canvas так же, как в лаб. 2. Отражение — только для показа: операции всё равно выполняются через сеть.
